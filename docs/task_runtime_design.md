# Task runtime — design doc

**Status:** Stage 1 BUILT behind `task_runtime.enabled` (default OFF). Architecture below; §9 tracks staging.
**Author:** design session with Ika, 2026-06-22.
**Scope:** the architecture for everything Mocha *does* (tasks), and the boundary that keeps everything she *is* (the relational soul) out of it.

## Implementation status (2026-06-22)

Stage 1 landed, flag-gated (`config.yaml: task_runtime.enabled: false`). Flip on after live validation; OFF = the graph behaves exactly as before.

- **Built + tested** (`bridge/test_task_runtime.py`, 27 tests; full suite 127 green): `bridge/task_store.py` (ActiveTask + 1-active/1-suspend store + timeout sweep), `bridge/task_templates.py` (registry + `fulfill` decision logic + `play_media`), the widened classifier (`interpret_node` → route/task_kind/task_slots), `task_step` node + the deterministic `video_player` ACT path, the `build_messages`/`task_step` topology, and the two independent fixes (§11) — both shipped, 31 parser tests green.
- **Stage 1.1 — built** (was deferred): the `fulfill` retry/ask-on-failure loop is graph-wired — `_advance_task_after_tools` reads the tool result and routes `run_tools → {llm_pass succeed | task_step retry | task_ask ask}`; `play_media` gets `retry_budget: 1` (one transient retry, then a parked clarifying question via `task_ask`). The background timeout sweep runs in the idle heartbeat (`_idle_heartbeat_loop`, off-turn so it never drops a task Ika is resuming), gated on the flag, TTL = `task_runtime.park_ttl_seconds`.
- **Verify the live happy path** once enabled: "find chopin on youtube" → plays immediately (no `web_search`, no permission question); "No. 2" → classifier resolves from history → plays No. 2.

## 0. Thesis in one line

> The state network defines what she's **doing**. The soul defines who she **is**. The network's only contribution to identity is *continuity of intention* — she remembers what she was doing and comes back to it.

Take that boundary seriously and this is the spine that fixes a whole class of bugs. Blur it — model the conversation itself as states — and she becomes an IVR with feelings. Section 2 is the most important section in this doc.

---

## 1. Why — the failure this fixes

### 1.1 The trace

"i want chopin piano concerto, find it on youtube" → "NO. 2" → "pull it up". From `logs/bridge.log`:

- **job=89** (after "NO. 2"): talk only, no tool — *"…Would you like to hear a recording?"* She asked permission for the thing already requested.
- **job=90**: `web_search` fired with an **empty query**, three times. Flailing.
- **job=92** (only after explicit "pull it up"): intent resolved to *"play Chopin Piano Concerto No.2"* → `video_player` → played first try.

`video_player` works. Everything before it was the system not knowing it was already mid-task.

### 1.2 The structural cause (confirmed in code)

- `bridge/graph_state.py`: `TurnState` is explicitly the state for **one** turn. The graph runs **with no checkpointer**. Nothing persists across turns.
- `bridge/session_scratchpad.py`: the only cross-turn memory is a **log of tool calls** — "what happened," not "what she's trying to do."
- `bridge/graph.py:interpret_node`: every turn, intent is **cold-read from history**. "No. 2" was read as a standalone trivia answer because nothing told the system there was an open goal it was a slot-fill for.

So abandonment is the *default*: a turn ends, no tool fired, the intent evaporates. **We are inverting that** — persistence becomes the default; giving up becomes an explicit edge.

### 1.3 Why prompting alone can't fix it

You'd be asking the model to reconstruct task state from 22 turns of history every turn and never whiff. It whiffs. A persistent goal object is deterministic where the prompt is probabilistic. Prompting makes a *single turn* smarter; it cannot make the *sequence* coherent.

## 2. The boundary (read this twice)

Two axes, kept separate:

| | Relational core | Task runtime |
|---|---|---|
| Answers | who she **is** | what she's **doing** |
| Mechanism | free-form LLM (soul.md) | state network |
| Covers | venting, curiosity, teasing, presence, opinions, idle/autonomy | play media, look up, remind, show, recall, brief |
| Share of turns | the **majority** | the minority |
| State machine? | **never** | always |

**Rule for the classifier:** default to the relational core. A turn enters the runtime only when it names a *task with a tool behind it*. Comfort, banter, a half-thought, a tangent — these never get a goal state. If we're unsure, it's relational.

The runtime *wraps* the soul; it does not replace it. **Inside any task state, the actual words are still generated by the soul-driven LLM.** The runtime decides *which* state and *whether to persist/interrupt/resume*; the LLM decides *what she says* and does the fuzzy judgments at the gates. Her voice never gets templated.

Non-goal: a flowchart per feature. That's how this idea dies in state-explosion. The universal piece is small (§4); capabilities are *instances of ~3 templates* (§5).

## 3. Architecture overview

```
                 ┌──────────────────────────┐
   every msg ──▶ │  classify (extend         │
                 │  interpret_node)          │
                 └─────┬───────────────┬─────┘
            "just talk"│               │"a thing to do"
                       ▼               ▼
          ┌────────────────┐   ┌───────────────────────────┐
          │ relational core│   │ task runtime              │
          │ free-form soul │   │ 1 active task + 1 suspend │  ◀─ v1: single slot
          │ (existing graph│   │ slot (continuation ptrs)  │
          │  unchanged)    │   └──────────┬────────────────┘
          └────────────────┘              │ instantiate
              the runtime                  ▼
              never reaches here   ┌───────────────────┐
                                   │ templates          │
                                   │ fulfill / slot-fill│
                                   │ / confirm          │
                                   └───────────────────┘
              lifecycle: interrupt → suspend · resume on answer · timeout → drop
```

The LLM threads through everything as **voice** (generation in every state) and **judgment** (classify at entry, answer-vs-pivot at the gates). The runtime owns control flow and persistence.

## 4. The task runtime (the universal spine)

Everything a task needs that is *not* template-specific lives here. This is the reusable layer; §5 templates plug into it.

### 4.1 The task object (a continuation pointer)

```python
@dataclass
class ActiveTask:
    kind: str            # "play_media" | "look_up" | "set_reminder" | ...
    template: str        # "fulfill" | "slot_fill" | "confirm"
    state: str           # current node within the template, e.g. "find" | "ask"
    slots: dict          # accumulated args, e.g. {"query": "chopin", "which": "2"}
    retry_count: int     # for fulfill-loop budgeting
    created_at: float
    last_active_at: float
    cancellable: bool = True
```

It is a *resume point*, nothing more: "parked at `ask` in `play_media`, slots={query: chopin}." Next turn resumes there instead of cold-reading history.

### 4.2 Lifecycle

```
                 ┌─ start ──▶ template runs ──▶ succeed ──▶ clear
   classify ─────┤
                 ├─ continue ─▶ resume at task.state (slot filled)
                 ├─ interrupt ─▶ suspend active, start new (push to slot)
                 └─ give-up / pivot ─▶ clear (and resume suspended if any)
   (background)  timeout ─▶ clear parked task after T idle
```

- **start**: no active task + message names a task → create `ActiveTask`, enter its template.
- **continue**: active task is parked (awaiting input) + message answers it → fill slot, resume template at `task.state`.
- **interrupt**: active task parked + message is a *different* task → suspend active into the suspend slot, start the new one. On the new task's exit, **resume** the suspended one (this is the "she remembers what she was doing" behavior — §6).
- **give-up / pivot**: active task parked + message is clearly an abandonment or a topic change → clear it. **This is the escape hatch**, and tuning its sensitivity is the single most important knob (§10.3).
- **timeout**: a parked task with no answer for `T` (default 10 min, tunable) is dropped by a background sweep so she isn't haunted by a stale goal.
- **exit**: every task ends in exactly one of `succeed | give_up | superseded`.

### 4.3 The entry classifier

Extends the existing `bridge/graph.py:interpret_node` — we are **not** adding a new component, we're widening the one that already reads intent.

- **Today**: gated to `_needs_interpret` (reply_context or ≤6-word turns), outputs `{asking, refers_to, needs_data, tool_hint, …}`.
- **Change**: also run whenever there is an active task (regardless of length), and feed it the active task. New output field:

```json
{ "route": "chat | start | continue | interrupt | give_up",
  "task_kind": "play_media | look_up | … | null",
  "slots": { "...": "..." } }
```

- `chat` → existing relational flow, untouched.
- `start` → create task, enter template.
- `continue` → the message is the answer to the parked `ask`; merge `slots`.
- `interrupt` → suspend + start.
- `give_up` → clear.

The classifier is the *only* place that decides chat-vs-task. Bias: when unsure between `chat` and anything else, choose `chat` (§2).

### 4.4 Where the runtime state lives

New module `bridge/task_store.py`, mirroring `session_scratchpad.py`:

- Per-`user_id` keyed (single-operator → effectively Ika, but keep the partition).
- In-RAM by default (tasks are seconds-to-minutes; a bridge restart dropping a parked task is acceptable and *safer* than resuming a stale one).
- Optional durable mirror to `data/users/{user_id}/active_task.json` if we later want restart survival.
- API: `get(user_id) -> ActiveTask|None`, `set(user_id, task)`, `suspend(user_id)`, `resume(user_id)`, `clear(user_id)`, `sweep_timeouts()`.

## 5. Templates (~3 carry everything)

A template is a tiny state machine + a contract for which node calls which tool. The Chopin machine is the `fulfill` template.

### 5.1 `fulfill` — search → maybe ask → act

States: `find`, `ask`. Terminals: `succeed`, `give_up`.

```
 find ──found──▶ succeed
 find ──need info / retries spent──▶ ask
 find ──retry (budget N)──▶ find
 ask  ──answer (next turn)──▶ find          ← the loop; clarifying ≠ exit
 ask  ──give-up / pivot──▶ give_up           ← the only non-success exit
```

- `find` calls the template's **primary tool deterministically** via `execute_tool` (for `play_media`: `video_player(action="open", query=slots.query)`). **No model tool-choice** — this is what structurally kills the empty-`web_search` flailing.
- On a clean result → LLM generates her spoken reaction → `succeed`.
- On ambiguity it can't resolve, or `retry_count >= N` → `ask`: LLM generates **one** clarifying question, task parks (`state="ask"`), turn ends.
- Next turn, classifier returns `continue` with the slot → resume at `find`.
- Exit conditions are the policy: you leave `{find, ask}` only via `succeed` or `give_up`. A vanity "want me to pull it up?" is **not a reachable state**.

### 5.2 `slot_fill` — collect fields → confirm → execute

States: `collect`, `confirm`. Terminals: `done`, `cancel`.
For reminders/cron: collect `{when, what}`, confirm once, then `execute_tool("schedule_cron", …)`. Same persistence/interrupt machinery; different shape (a form, not a search loop).

### 5.3 `confirm` (degenerate, one node) — immediate UI actions

`show_diary`, `show_slides`, `show_card`, `clear_ui`, `mute`, `video_player(close)`. No loop, no parking — they fire the tool and exit `done` in the same turn. They live here only to share the entry/exit plumbing (and so "open it again" routes cleanly).

## 6. Capability → template map

| Capability | Tool(s) | Template |
|---|---|---|
| Play media | `video_player(open, query)` | fulfill |
| Web lookup / "what is X" | `web_search` | fulfill |
| Price / news / weather | `get_stock_data`, `get_news`, `get_weather` | fulfill |
| Position brief / desk briefing | `get_position_brief`, `get_trading_briefing`, … | fulfill |
| Recall a diary day | `recall_diary` | fulfill |
| Set reminder / routine | `schedule_cron` | slot_fill |
| Set display name | `set_display_name` | slot_fill (1 field) |
| Show diary / slides / card | `show_diary`, `show_slides`, `show_card` | confirm |
| Mute / close / clear | `mocha_self_mute`, `video_player(close)`, `clear_ui` | confirm |
| **Everything relational** | — | **none (free-form)** |

Most tools are `fulfill`. The universal spine + three templates cover the whole toolkit; the soul covers everything else.

### 6.1 The suspend/resume payoff (why this feels like a person)

Mid-`fulfill` of the concerto, Ika asks "what's NVDA at?" → classifier returns `interrupt` → concerto task suspends → price `fulfill` runs and succeeds → runtime **resumes** the concerto task and she picks it back up ("anyway — No. 2, pulling it up"). Continuity of intention across an interruption. This is the property prompting can never fake, and it's a lot of what reads as "she was paying attention."

## 7. graph.py integration

The relational path stays **exactly as-is**. We add a task lane.

```
START
  └─▶ router (existing)
        └─▶ classify  (interpret_node, widened §4.3)
              ├─ route=chat ───────────▶ build_messages ─▶ llm_pass ─▶ … (UNCHANGED)
              └─ route∈{start,continue,interrupt} ─▶ task_step  (new)
                                                        │
                            ┌── needs a clarifying Q ───┤
                            ▼                           │
                       (park task, emit Q) ─▶ finalize  │
                            ┌──────────────── act / succeed
                            ▼
                       run primary tool via execute_tool ─▶ llm synth reaction ─▶ finalize
```

- **New node `task_step`**: loads `ActiveTask`, runs one step of its template. It *reuses* existing primitives — `execute_tool` (`tools/executor.py:70`), `_synthesize`, the inline-tag generation, the `emit` queue — so streaming/voice/timing are identical to today. It does **not** reuse the free-form `llm_pass` tool-choice loop for the primary action; that's the point.
- **Store threading**: `_run_inline_turn` (`server.py:1509`) loads the active task and puts it in the `init` dict alongside `user_id`; `task_step` reads/writes via `bridge/task_store.py`.
- **Timeout sweep**: piggyback on the existing autonomy/idle loop (`autonomy/presence.py`) or a small periodic task → `task_store.sweep_timeouts()`.
- **Interaction with fast/deep routing & `<escalate/>`**: task turns force `deep` (tools live there) and skip the fast-model escalation dance — the runtime already knows it's a task, so there's nothing to self-escalate. The relational path keeps fast/deep + escalate unchanged.

## 8. Prompt changes that come with this

- **Delete the contradiction.** `character/behaviors.yaml` media rule currently says *"web_search for the match, then call video_player"* — the exact instruction that caused the empty-search loop. Under the runtime the `find` node owns the tool call, so this rule is replaced by template logic. (Land the deletion now regardless — see §11.)
- **The tools block in `character/context.py` becomes advisory, not load-bearing**, for anything that's now a template. The model no longer has to choose/format the primary tool call for a task; it reacts to the result. Keep the block for the relational path's incidental tool use.
- **Soul untouched.** `character/soul.md` and the relational behavior rules do not change. That's the boundary holding.

## 9. Staged rollout

Always keep a working spine; never a big-bang rewrite.

1. **Runtime + `fulfill` + `play_media`.** Build `task_store.py`, the widened classifier, `task_step`, and the `fulfill` template with `video_player` as the first primary tool. Proves the whole architecture end-to-end and fixes the live bug. Single suspend slot.
2. **Migrate the other `fulfill` tools** (lookups, prices/news/weather, briefings, recall) onto the template. Mostly config — each is a `{kind, primary_tool, slot_schema}` entry.
3. **`slot_fill` template** (reminders/cron, set name).
4. **`confirm` template** for immediate UI actions (cheap cleanup; mostly moving existing tool calls behind the entry/exit plumbing).

Relational core untouched throughout. Each stage is independently shippable and reversible.

## 10. Decisions & open questions

### 10.1 Stack depth — DECIDED: single slot for v1
One active + one suspended. Covers the real interrupt-and-resume case. A full agenda stack (interrupt an interrupt) is a clean upgrade — `task_store` holds a list instead of a slot — deferred until a real need appears.

### 10.2 Classifier cost/latency — OPEN
The widened `interpret_node` runs on more turns now (any turn with an active task). It's already a cheap, fast-model, no-thinking call. Measure added TTFT on task turns; if it bites, gate harder (only re-classify when an active task is *parked*, not while it's mid-find).

### 10.3 Escape-hatch sensitivity (`ask → give_up` on pivot) — OPEN, the key knob
Too eager = we've reinvented today's silent-drop. Too sticky = kiosk that won't let Ika change the subject. Start conservative (require a *clear* pivot or explicit "nvm"; ambiguous → stay parked and let timeout handle the rest) and tune from real transcripts.

### 10.4 Eval plan — OPEN
Replay the Chopin transcript + a handful of hand-written task/interrupt/pivot sequences through the runtime in `bridge/test_graph_*`. Assert: "No. 2" resumes the find (not trivia); an interrupt resumes afterward; an explicit "nvm" clears; a parked task times out.

## 12. Risks

- **Companion-killing (highest):** over-applying the network into conversation. Mitigation: §2 boundary, classifier defaults to `chat`, soul untouched.
- **State-explosion:** mitigated by ~3 templates instantiated per capability, not bespoke graphs.
- **Stale-goal haunting:** mitigated by the timeout sweep (§4.2).
- **Latency:** one extra cheap classify call on task turns; measured in §10.2.
- **Regression on the relational path:** mitigated by leaving it literally unchanged (§7).
